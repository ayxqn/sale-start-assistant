# 当前 APK 与旧 V2.4 流程的差异

[项目首页](../README.md) · [文档导航](README.md) · [测试与验收](TESTING.md)

2026 年 9 月 30 日，对照本地标为 `2.4.0` 的旧程序源码和本仓库 `1.0.0` APK 核查。旧源码是 AutoJs6 脚本方案；当前 APK 是独立 Java 应用。**当前版本不是旧抢购流程的功能等价移植，不能当作该目标已经完成的交付。**

用户反馈旧版曾成功购买。此次没有读取账号凭据、订单或支付记录，也没有与成功运行当时手机文件的哈希对照，因此只确认本地备份的代码行为，不据此否定用户的实际结果。

## 逐项对照

| 流程 | 本地旧 V2.4 代码 | 当前 1.0.0 APK |
| --- | --- | --- |
| 登录会话 | 从手机私有目录解密导入的登录会话，读取 Cookie 和 CSRF 等字段，向官方接口验证账号。没有从已安装 B 站 App 偷读登录数据的流程。 | 没有读取、导入或保存登录会话；只让用户在官方 App 登录。 |
| 会话保存 | 原电脑登录使用 Windows DPAPI 保存会话，经本地 USB 转发导入；手机用 AndroidKeyStore 与 RSA-OAEP 加密保存。旧导入工具还带历史测试付款数据，不适合原样交给其他人。 | 只保存普通活动名称、公开链接和时间，不保存账号或订单。 |
| 服务端校时 | 读取官方活动 `current_time`，结合发送、接收的单调时钟做多样本区间校准；开售前校时并再次刷新商品。 | 只按手机时间做本地倒计时，没有服务端校时。 |
| 商品核对 | 核对特定限量组合、金额和商品身份，避免同价不同套餐。 | 不解析商品或套餐，只校验活动页链接。 |
| 创建订单 | 调用官方活动创建订单接口，识别成功、尚未开售、繁忙、售罄、限流及结果不明等响应。 | 没有创建订单代码。 |
| 串行重试 | 只有明确没有订单且属于特定可重试回复时继续；一次等完上一笔响应后再发。取得订单、售罄、验证限制、错误金额、未知结果和超时会停止。 | 没有任何下单或付款重试。 |
| 微信付款交接 | 取得订单后做收银台安全检查、查询渠道并申请微信预支付凭证，打开微信或回退官方收银台；最终密码或指纹付款由本人确认。 | 只打开官方活动页，不办理微信预支付或收银台交接。 |

旧源码主要依据：`phone-api.js` 的 `session`、`headers`、`check`、`calibrateActivityClock`、`prepareWechat`、`launchWechat`；`limited-flow.inc.js` 的 `runLimited` 与 `submitLimited`；`purchase-core.js` 的响应分类和重试决策；`activity-clock.js` 的校时数学。原始个人实验文件不随本仓库发布。

## 连续下单不等于连续扣款

旧代码连续请求的是创建订单。它仅在明确回复尚未开售，或特定繁忙回复且没有订单引用时重试。拿到订单就退出创建循环。

微信预支付凭证申请有订单级一次性标记，防止对同一订单自动反复申请。付款确认仍由用户在官方付款应用完成。此次没有执行任何真实请求，不能把离线模拟中的“创建成功”当成真实订单或扣款。

## 此次离线验证

已检查测试代码的执行边界后，运行旧源码现有测试：62 项购买流程分类与模拟、10 项活动时钟数学检查、校时策略模拟，以及启动网络探测策略模拟，均通过。它们使用合成回复和内存传输，没有网络、真实下单、付款或账号凭据读取。

当前 APK 的构建、签名和 30 项本地规则检查仍有效，但不覆盖旧版接口流程，也不证明恢复后的版本已经可用。当前 APK 尚未完成真机或模拟器运行验收。

## 恢复完整目标需要做什么

旧版规则和校时算法可以作为迁移依据，但不能把用户的旧会话、订单文件或支付签名打包到新应用里。

独立 APK 需要重新实现每个使用者自己的登录与退出、AndroidKeyStore 保护、本机账号隔离、官方请求、商品身份核对、服务端校时、订单状态和防重复处理，以及付款交接。实际接口可用性和移动登录流程还需要单独验证。旧代码固定适配特定活动，并非任意购物链接都能使用。

恢复这些联网流程后，安装清单和隐私说明必须同步更新，不能继续套用当前版本“不联网、不处理账号”的说明。最终仍需构建、签名、离线异常场景测试和手机验收，再提供与真实功能一致的新版本安装包。当前 1.0.0 不能作为这个目标的最终 APK 发送。
